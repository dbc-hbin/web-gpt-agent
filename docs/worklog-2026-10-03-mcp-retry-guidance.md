Leading-code rejection entries included `CODE_MODE_SCRIPT_ERROR` 64, `CODE_MODE_PARSE_ERROR` 43, `CODE_MODE_UNKNOWN_CELL` 32, `CODE_MODE_OUTPUT_LIMIT` 27, `WORKER_CONNECTION_REQUIRED` nine and `EXEC_RESULTS_UNREAD` six. - The eight failed guard entries belonged to searches. Local `tool_rejected`, `tool_internal_error`, command exit codes and numeric `403` matches do not establish OpenAI security rejection. No provider-security refusal was established in this snapshot; a refusal before server ingress can be absent from local logs.
- At the user's direction, the 2026-09-23 experiment history was checked separately. Its retained native tool-result extraction contains two distinct OpenAI messages: a safety-check block (`OpenAI의 안전 검사에서 이 도구 요청을 차단했습니다. 전송하는 항목을 재차 확인하세요.`) and inability to determine security status (`요청의 보안 상태를 결정하지 못해 이 도구 요청은 OpenAI에 의해 차단되었습니다.`). Both exact strings were independently extracted from the original historical tool-result output, not only a prior assistant summary. No numeric provider error code was observed in that evidence. Thus the current local-log snapshot does not erase the earlier reproduced provider-side blocks. Private session identifiers and experiment task contents are omitted.

Native refusal objects support both reports, but equivalent operations changed outcomes between runs and narrower individual calls could still be blocked. Scope narrowing and precise arguments are an operational retry recommendation, not a demonstrated guaranteed cure. Earlier case reports correlated blocked cases with no app execution record; this review independently confirmed native errors and local outcome categories, but did not independently reconstruct every per-call ingress correlation. No provider experiment was rerun.
